## 引言
本指南旨在总结axvisor在实际使用中的核心最佳实践，涵盖性能优化、安全性考量及常见问题解决方案。通过分析多虚拟机并发运行时的资源配置、SMP调度机制、磁盘镜像自动化管理以及安全隔离策略，为开发者和运维人员提供可落地的操作指导。文档结合`SMP.md`、`GuestVMs.md`等官方说明与具体配置文件（如`.toml`模板）进行深入解读，并推荐利用`disk_img.py`脚本提升操作效率。

## 性能优化与资源分配策略

在多虚拟机并发运行场景下，合理的vCPU数量与内存大小配置是避免资源争抢的关键。每个虚拟机应根据其负载特性分配专属物理核心，防止跨核竞争导致上下文切换开销增加。

对于计算密集型客户机（如ArceOS或Linux），建议将`cpu_num`设置为偶数并绑定到非相邻的物理核心组，以减少缓存行伪共享。例如，在`arceos-aarch64-e2000-smp2.toml`中，通过`phys_cpu_ids = [0x201, 0x100]`和`phys_cpu_sets = [2, 8]`实现vCPU与特定物理核心的绑定，确保调度确定性。

内存方面，应依据客户机操作系统需求设定`memory_regions`参数。例如，Linux客户机通常需要更大的系统RAM区域（如`0x4000_0000`即1GB），而轻量级实时系统NimbOS仅需少量内存（如`0x100_0000`即16MB）。同时，使用`MAP_IDENTICAL`映射类型可提高地址转换效率。

## SMP多核调度配置建议

当前axvisor的SMP支持基于静态vCPU绑定机制，因缺乏中断虚拟化功能，每个vCPU被固定映射至特定物理核心。未来一旦支持中断虚拟化，将启用灵活的多对多调度模式。

参考`SMP.md`文档，配置多核客户机时需重点关注以下三个参数：
- `cpu_num`：定义客户机所需vCPU数量。
- `phys_cpu_ids`：表示从客户机视角看到的物理CPU ID，可能因平台设计呈非连续分布。
- `phys_cpu_sets`：定义各vCPU的亲和性位图，控制其可运行的物理核心集合。

例如，一个四核配置示例：
```toml
cpu_num = 4
phys_cpu_ids = [0x00, 0x100, 0x200, 0x300]
phys_cpu_sets = [0x1, 0x2, 0xC, 0xC]
```
其中前两个vCPU分别独占核心0和1，后两个vCPU可在核心2或3上调度，适用于主从架构任务模型。

启动命令示例：`make ARCH=aarch64 VM_CONFIGS=configs/vms/arceos-aarch64-smp.toml SMP=2 run`

## 磁盘镜像管理最佳方式

针对不同客户机操作系统（ArceOS/Linux/Nimbos），推荐使用`disk_img.py`脚本统一管理磁盘镜像创建流程，实现自动化与一致性。

该脚本位于`scripts/disk_img.py`，主要功能包括：
- 自动检测并安装arceos依赖；
- 接收用户指定的镜像路径（支持相对/绝对路径）；
- 调用底层`make disk_img`命令生成标准化FAT32格式镜像；
- 输出执行状态与错误信息，便于调试。

使用方法示例：
```bash
python3 scripts/disk_img.py --image ./images/disk.img
```

此方式避免了手动构建过程中的路径错误与权限问题，尤其适合CI/CD流水线集成。

## 安全边界设置与隔离机制

为防止恶意客户机突破隔离，必须严格配置设备透传与内存映射边界。所有客户机的`passthrough_devices`列表应仅包含必要的硬件外设，且基地址与长度需精确限定。

例如，在`nimbos-aarch64-qemu-smp1.toml`中，仅透传串口（pl011）、RTC（pl031）和GIC中断控制器，未暴露其他PCIe或DMA设备，有效缩小攻击面。

此外，内存区域应采用最小权限原则分配标志位（`flags`字段），禁用不必要的读写执行权限组合。建议对只读固件区域设置`EXECUTE | READ`，数据区设置`READ | WRITE`，避免代码注入风险。

VMM层还应在初始化阶段验证客户机配置合法性，如`build.rs`中所示，若配置文件无法解析则触发编译期错误，阻止不安全镜像加载。

## 典型故障排查路径

### 启动失败
检查点：
1. 配置文件路径是否正确（由`AXVISOR_VM_CONFIGS`环境变量指定）；
2. 内核镜像路径是否存在且可读（`kernel_path`字段）；
3. 物理CPU ID是否匹配宿主机拓扑（见`phys_cpu_ids`）；
4. 日志输出中是否有`compile_error!`或`panic!`信息。

工具链：使用`make ... run`时观察终端输出，结合`dmesg`查看内核日志。

### 性能瓶颈
诊断步骤：
1. 使用`perf`监控物理核心利用率，确认是否存在vCPU争抢；
2. 检查`phys_cpu_sets`是否合理分配，避免多个vCPU绑定同一核心；
3. 分析客户机内部调度延迟，判断是否需调整`timer`中断频率；
4. 查看`memory_regions`是否足够，避免频繁换页。

### 通信中断
排查方向：
1. 确认`ivc`（Inter-VM Communication）通道已正确定义；
2. 检查`interrupt_mode = "passthrough"`是否启用；
3. 验证透传设备的IRQ分配无冲突；
4. 使用`telnet localhost <port>`测试串口连通性（如`SECOND_SERIAL=y`启用时）。

## 生产环境部署经验

### 监控指标采集
建议在VMM层暴露关键性能计数器，如：
- vCPU调度次数与上下文切换耗时；
- 内存分配成功率与碎片率；
- IVC消息吞吐量与延迟；
- 设备访问异常次数。

可通过扩展`axhvc`接口实现宿主机侧数据拉取。

### 日志分析
启用详细日志级别（`log = "=0.4.21"`），并将日志重定向至独立存储分区。利用结构化日志工具（如`journalctl`或ELK栈）过滤`warn!`及以上级别事件，重点关注`VM boot failed`、`Hypercall failed`等关键字。

### 容灾恢复策略
1. **配置备份**：定期归档`configs/vms_bkp/`目录下的`.toml`文件；
2. **镜像快照**：对`disk.img`实施增量备份；
3. **快速回滚**：维护默认配置模板（如`def_hvconfig.toml`），支持一键还原；
4. **健康检查**：部署守护进程周期性ping客户机心跳端口，自动重启异常实例。

以上实践已在RK3588等真实硬件平台上验证，显著提升了系统稳定性与可维护性。
