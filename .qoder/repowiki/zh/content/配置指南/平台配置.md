## 平台配置概述

平台配置系统是本项目中用于定义目标硬件虚拟化环境的核心机制。该系统通过位于`configs/platforms/`目录下的TOML格式配置文件，精确描述了不同硬件平台的物理内存布局、设备地址映射、中断控制器参数等关键信息。这些配置文件为虚拟机监控器（Hypervisor）提供了初始化和管理虚拟化环境所需的全部硬件抽象信息。

每个平台配置文件以特定命名约定标识其适用的目标架构和硬件平台，例如`aarch64-qemu-virt-hv.toml`表示适用于在QEMU模拟器上运行的AArch64架构通用虚拟平台。这些配置文件不仅定义了静态的硬件资源布局，还包含了动态的启动选项和虚拟化特性设置，确保Hypervisor能够正确地为特定平台创建和管理虚拟机实例。

## 平台配置文件结构详解

平台配置文件采用分层的TOML结构组织，主要包含架构标识、平台家族、物理内存布局和设备规格等核心部分。

### 架构与平台标识

配置文件开头定义了基本的架构和平台信息：
```toml
arch = "aarch64"
platform = "aarch64-qemu-virt-hv"
```
其中`arch`字段指定目标CPU架构，而`platform`字段提供唯一的平台标识符，用于在构建和运行时区分不同的硬件配置。

### 物理内存布局规划

`[plat]`表项详细定义了物理内存的关键参数：
- `phys-memory-base`: 物理内存起始地址
- `phys-memory-size`: 物理内存总大小
- `kernel-base-paddr`: 内核镜像的物理基地址
- `kernel-base-vaddr`: 内核镜像的虚拟基地址
- `phys-virt-offset`: 物理地址与虚拟地址之间的线性映射偏移量

这些参数共同构成了内核地址空间的基础，确保了物理内存与虚拟内存之间的正确映射关系。

### 设备规格定义

`[devices]`表项是配置文件中最复杂的部分，它定义了各种硬件设备的地址空间和中断配置：
- `mmio-regions`: 标准MMIO区域列表，包含基础物理地址和大小
- `virtio-mmio-regions`: VirtIO设备专用的MMIO区域
- `pci-ecam-base`: PCIe ECAM（Enhanced Configuration Access Mechanism）基地址
- `uart-paddr` 和 `uart-irq`: UART串口设备的物理地址和中断号
- GIC相关地址：包括`gicc-paddr`（GIC CPU接口）、`gicd-paddr`（GIC分发器）等

特别值得注意的是，对于使用GICv3中断控制器的平台，配置文件还定义了`gicr-paddr`（GIC重分布器基地址），这对于多核系统的中断管理至关重要。

## 默认平台配置机制

`def_hvconfig.toml`文件作为默认平台配置模板，在项目初始化和构建过程中扮演着重要角色。该文件不直接定义具体的硬件平台，而是提供了一套可继承和覆盖的默认配置参数。

### 核心配置字段

```toml
plat = "aarch64-generic"
features = ["ept-level-4"]
arceos_args = ["BUS=mmio", "BLK=y", "MEM=8g", "LOG=debug", "QEMU_ARGS=\"-machine gic-version=3  -cpu cortex-a72  \""]
arceos_features = []
vmconfigs = []
```

- `plat`: 指定默认的目标平台，通常指向一个通用平台实现
- `features`: 定义编译时启用的功能特性，如EPT四级页表支持
- `arceos_args`: 传递给ArceOS操作系统的启动参数，包括总线类型、块设备支持、内存大小和日志级别等
- `vmconfigs`: 空列表，用于后续通过环境变量注入具体的虚拟机配置

这个默认配置文件的设计允许开发者在不修改源码的情况下，通过简单的配置文件复制和修改来快速适配新的硬件平台。

## 构建期配置处理流程

平台配置文件在编译期间通过`build.rs`构建脚本被解析并转换为静态Rust代码，供HAL层调用。这一过程实现了配置数据的编译时确定性和零运行时开销。

### 构建脚本工作机制

`build.rs`脚本通过读取`AXVISOR_VM_CONFIGS`环境变量获取配置文件路径列表，并执行以下关键步骤：

1. **配置文件读取**: 使用`get_configs()`函数读取所有指定的TOML配置文件内容
2. **输出文件生成**: 在`$(OUT_DIR)/vm_configs.rs`中生成包含配置内容的Rust代码
3. **静态函数定义**: 创建`static_vm_configs()`函数，返回包含所有配置文件内容的字符串向量

当`AXVISOR_VM_CONFIGS`环境变量未设置时，系统会自动回退到`src/vmm/config.rs`中定义的`default_static_vm_configs()`函数，使用内置的默认配置。

### 配置到代码的转换

构建脚本将TOML配置文件的内容直接嵌入到生成的Rust代码中：
```rust
pub fn static_vm_configs() -> Vec<&'static str> {
    vec![
        r###"[原始TOML内容]"###,
    ]
}
```
这种设计确保了配置数据在编译时就被固化到二进制文件中，避免了运行时文件I/O操作，提高了系统启动效率和可靠性。

## 新增自定义平台流程

为新硬件平台（如基于RK3588的变种）添加支持需要遵循一系列标准化步骤，确保配置的一致性和正确性。

### 创建新平台配置

1. **复制模板**: 从相似平台的配置文件开始，例如：
   ```bash
   cp configs/platforms/aarch64-rk3588j-hv.toml configs/platforms/aarch64-rk3588-custom-hv.toml
   ```

2. **修改寄存器地址映射**: 根据新平台的硬件手册更新关键设备的物理地址：
   - 调整`mmio-regions`中的UART、RTC等外设地址
   - 更新`virtio-mmio-regions`的基地址和大小
   - 修正PCIe ECAM基地址`pci-ecam-base`

3. **验证设备初始化顺序**: 确保配置中的设备地址不冲突，并符合硬件启动要求。特别是要注意：
   - MMIO区域不能重叠
   - 中断控制器配置必须与实际硬件匹配
   - 内存映射区域要避开保留区域

### 集成到构建系统

通过设置`AXVISOR_VM_CONFIGS`环境变量将新配置纳入构建流程：
```bash
export AXVISOR_VM_CONFIGS="configs/platforms/aarch64-rk3588-custom-hv.toml"
```

构建系统会自动检测配置文件的变化并重新生成相应的Rust代码，确保新平台配置被正确编译进最终的二进制文件。

## 常见错误排查

在配置新平台时，可能会遇到一些典型问题，以下是常见的错误及其解决方案。

### MMIO区域冲突

**现象**: 系统启动失败或设备无法正常工作  
**原因**: 两个或多个设备的MMIO地址范围发生重叠  
**解决方案**: 
1. 使用`mmio-regions`列表仔细检查所有设备的地址分配
2. 确保每个设备的`[base, base+size)`区间互不相交
3. 参考硬件手册确认正确的地址映射

### 中断配置错误

**现象**: 设备中断无法触发或系统不稳定  
**原因**: GIC相关地址配置不正确或中断号冲突  
**解决方案**:
1. 验证`gicd-paddr`、`gicc-paddr`和`gicr-paddr`是否与硬件规格一致
2. 检查`uart-irq`等设备中断号是否在有效范围内
3. 确认PSCI方法（`psci-method`）与平台兼容

### 内存布局问题

**现象**: 内核无法启动或内存访问异常  
**原因**: 物理内存基地址或大小配置错误  
**解决方案**:
1. 核对`phys-memory-base`和`phys-memory-size`是否准确
2. 确保`kernel-base-paddr`位于有效的物理内存范围内
3. 验证`phys-virt-offset`计算是否正确，保证物理地址到虚拟地址的转换无误

通过遵循上述指导原则和排查方法，可以有效地创建和调试新的平台配置，确保Hypervisor能够在目标硬件上稳定运行。
