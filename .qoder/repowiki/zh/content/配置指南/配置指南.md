## 简介
本指南系统性地介绍axvisor的配置体系结构，涵盖平台特定配置、虚拟机配置、默认配置机制以及编译期配置处理流程。文档详细解释了各配置文件的作用、字段含义、优先级规则和迁移方法，为用户提供了完整的配置管理指导。

## 平台配置体系

`configs/platforms/`目录下的TOML文件用于定义特定硬件平台的虚拟化参数，每个文件对应一个具体的硬件平台或QEMU模拟环境。这些配置文件包含了CPU架构、内存布局、中断控制器、设备地址空间等关键信息。

以`aarch64-qemu-virt-hv.toml`为例，该文件定义了在QEMU虚拟环境中运行Aarch64架构所需的完整平台信息：

- **架构标识**：通过`arch`字段指定目标架构（如"aarch64"）
- **物理内存配置**：`phys-memory-base`和`phys-memory-size`定义了物理内存的基地址和大小
- **内核映像地址**：`kernel-base-paddr`和`kernel-base-vaddr`分别指定内核映像的物理和虚拟基地址
- **设备规范**：包括MMIO区域、VirtIO设备、PCIe配置空间等
- **中断控制器**：GIC（通用中断控制器）的各个组件（GICC、GICD、GITS、GICR）的基地址
- **UART配置**：串口设备的物理地址和中断号

这些平台配置被构建系统读取，用于生成针对特定硬件平台的静态常量，确保hypervisor能够正确初始化和管理底层硬件资源。

## 虚拟机配置结构

`configs/vms/`目录中的虚拟机配置文件定义了客户机操作系统的具体参数，采用模块化的TOML格式组织。配置文件主要分为三个部分：基础信息、内核配置和设备规范。

### 基础信息配置
```toml
[base]
id = 2
name = "arceos"
vm_type = 1
cpu_num = 1
phys_cpu_ids = [0x00]
phys_cpu_sets = [4]
```
- `id`：虚拟机唯一标识符
- `name`：虚拟机名称
- `vm_type`：虚拟化类型
- `cpu_num`：vCPU数量
- `phys_cpu_ids`和`phys_cpu_sets`：物理CPU分配策略

### 内核配置
```toml
[kernel]
entry_point = 0x20_2008_0000
image_location = "memory"
kernel_load_addr = 0x20_2008_0000
kernel_path = "/path/to/arceos_aarch64-dyn_smp1.bin"
dtb_load_addr = 0x20_2000_0000
dtb_path = "/path/to/axvisor/configs/vms/arceos-aarch64-e2000_smp1.dtb"
memory_regions = [
    [0x20_2000_0000, 0x2000_0000, 0x7, 1],
]
```
- `entry_point`：内核入口点地址
- `image_location`：镜像加载位置（"memory"表示从内存加载）
- `kernel_path`：内核镜像文件路径
- `dtb_path`：设备树二进制文件路径
- `memory_regions`：内存区域配置，包含基地址、大小、标志位和映射类型

### 设备规范
```toml
[devices]
passthrough_devices = [
    ["UART1", 0x2800_d000, 0x2800_d000, 0x1000, 0x1],
    ["gic-v3", 0x3080_0000, 0x3080_0000, 0x10000, 0x1],
]
```
- `passthrough_devices`：直通设备列表，允许虚拟机直接访问物理设备
- 每个设备条目包含名称、IPA（中间物理地址）、PA（物理地址）、长度和分配的中断号

## 旧版配置迁移

`vms_bkp`目录保存了旧版本的虚拟机配置文件，与当前`vms`目录中的配置相比存在命名约定和结构上的差异。主要变化包括：

1. **命名规范变更**：旧版使用下划线分隔符（如`arceos-aarch64-e2000_smp1.toml`），新版统一使用连字符（如`arceos-aarch64-e2000-smp1.toml`）
2. **配置结构优化**：新版配置文件采用了更清晰的模块化结构，将相关配置项归类到不同的表（table）中
3. **字段语义明确化**：部分字段的命名更加准确地反映了其用途

迁移步骤：
1. 复制旧版配置文件到`configs/vms/`目录
2. 修改文件名，将下划线替换为连字符
3. 检查并更新配置结构，确保符合新版格式要求
4. 验证路径引用是否正确，特别是`kernel_path`和`dtb_path`字段

通过对比`arceos-aarch64-e2000_smp1.toml`（旧版）和`arceos-aarch64-e2000-smp1.toml`（新版）可以发现，除了命名差异外，配置内容基本保持一致，这保证了向后兼容性。

## 默认配置与优先级规则

axvisor提供了两个默认配置文件：`def_hvconfig.toml`和`defconfig.toml`，它们构成了系统的基础配置框架，并遵循特定的优先级覆盖机制。

### def_hvconfig.toml
此文件定义了hypervisor的核心配置：
- `plat`：指定默认平台（如"aarch64-generic"）
- `features`：构建特性列表
- `arceos_args`：传递给ArceOS的构建参数
- `vmconfigs`：虚拟机配置列表

### defconfig.toml
此文件包含运行时的基本参数：
- `task-stack-size`：任务栈大小
- `ticks-per-sec`：每秒定时器滴答数
- `smp`：CPU核心数量

### 优先级覆盖机制
配置系统的优先级顺序如下（从高到低）：
1. 命令行参数
2. `.hvconfig.toml`（用户自定义配置文件）
3. `def_hvconfig.toml`（默认配置）

当同一配置项在多个层级出现时，高优先级的值会覆盖低优先级的值。例如，如果在命令行中指定了`--plat=aarch64-qemu-virt-hv`，则无论配置文件中如何设置，都将使用QEMU虚拟平台。

这种分层配置机制提供了极大的灵活性，允许用户在不修改源码的情况下定制系统行为。

## 编译期配置处理机制

axvisor的配置系统在编译期通过`build.rs`构建脚本进行处理，实现了配置的静态化和代码生成。这一过程确保了配置信息能够在运行时高效访问，同时保持了良好的可维护性。

### 构建流程
1. **环境变量读取**：构建脚本首先检查`AXVISOR_VM_CONFIGS`环境变量，该变量包含一个由冒号分隔的配置文件路径列表
2. **配置文件解析**：读取指定路径下的所有TOML配置文件，并验证其有效性
3. **代码生成**：将配置文件内容转换为Rust代码，生成`$(OUT_DIR)/vm_configs.rs`文件

### 关键实现
`build.rs`脚本的核心功能包括：
- `get_configs()`函数：获取并解析配置文件路径
- `parse_config_file()`函数：提取配置文件中的镜像路径信息
- `generate_guest_img_loading_functions()`函数：生成包含`include_bytes!`宏的Rust代码，将镜像文件嵌入到可执行文件中

生成的`vm_configs.rs`文件包含两个重要函数：
- `static_vm_configs()`：返回配置文件内容的静态字符串向量
- `get_memory_images()`：返回预加载的镜像数据，包括内核、DTB、BIOS和ramdisk

如果未设置`AXVISOR_VM_CONFIGS`环境变量，系统将回退到使用`src/vmm/config.rs`中定义的`default_static_vm_configs()`函数提供的默认配置。

这种编译期配置处理机制不仅提高了运行时性能（避免了文件I/O操作），还增强了系统的可靠性和安全性。

## 自定义配置创建指南

创建新的平台或虚拟机配置需要遵循以下步骤：

### 创建新平台配置
1. 在`configs/platforms/`目录下创建新的TOML文件，命名格式为`<arch>-<platform>-hv.toml`
2. 参考现有配置文件，填写必要的平台参数
3. 确保所有地址和大小值使用正确的十六进制格式
4. 验证配置文件的语法正确性

### 创建新虚拟机配置
1. 在`configs/vms/`目录下创建新的TOML文件，命名格式为`<guest>-<arch>-<platform>-smp<n>.toml`
2. 定义基础信息（ID、名称、vCPU数量等）
3. 配置内核参数，包括入口点、加载地址和镜像路径
4. 设置内存区域和设备直通规则

### 验证方法
1. 设置`AXVISOR_VM_CONFIGS`环境变量指向新创建的配置文件
2. 执行构建命令，观察是否有配置解析错误
3. 运行生成的hypervisor，检查虚拟机是否能正常启动
4. 使用调试工具验证内存布局和设备映射是否正确

通过遵循这些步骤，用户可以轻松地为新的硬件平台或客户机操作系统创建和验证自定义配置，充分发挥axvisor的灵活性和可扩展性。
